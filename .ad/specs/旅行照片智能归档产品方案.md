# 旅行照片智能归档产品方案

> 本文是产品想法原文（偏完整愿景）。  
> **本仓库正在落地的范围、表设计、开发进度和测试记录**见：  
> [`.ad/specs/ai-travel-assistant/photo-archive-journal.md`](../../.ad/specs/ai-travel-assistant/photo-archive-journal.md)  
>  
> 与仓库不一致时以开发实录为准。已拍板的差异：不做 `PhotoOrganizerGraph`（改用独立 `photo_jobs` 工作流）；照片挂 `trip_id` 不挂登录用户；第一期不做视觉识别、不按照片改行程。

## 一、产品定位

在现有旅行规划 Agent 的基础上，增加“基于行程上下文的智能旅行相册归档”能力。用户完成旅行规划或旅行结束后，可以批量上传照片，系统根据照片中的 GPS、拍摄时间、图片内容和当前行程信息，将照片自动归档到对应的日期、景点和行程节点中。

典型流程：

> 用户上传 200 张照片 → 系统解析照片信息 → 自动识别带 GPS 的照片 → 匹配到对应行程节点 → 对无 GPS 照片结合拍摄时间、视觉内容和当日路线进行推断 → 输出分类结果和待确认照片。

最终可在行程详情页中提供：

- 每个行程节点对应的照片墙。
- 查看某个地点照片的功能。
- 未归类照片列表。
- 照片所属地点和置信度展示。
- 用户手动修改照片归属的入口。
- 根据照片反向补充旅行记录或生成游记。

## 二、总体设计原则

不建议让 LLM 直接对照片进行无约束的地点猜测，而应采用分层处理方式：

1. 元数据优先：优先读取 GPS 和拍摄时间。
2. 行程约束：候选地点优先来自当前行程数据库。
3. 视觉识别兜底：使用多模态模型识别地标、文字和场景特征。
4. 置信度分级：高置信度自动归档，低置信度交给用户确认。
5. 结果可解释：保存距离、时间、视觉识别结果等判断依据。
6. 隐私保护：明确告知用户照片用途，支持删除原图和关闭视觉分析。

ExifTool 可用于读取、写入和编辑 JPEG 等文件中的 EXIF、GPS、IPTC 和 XMP 等元数据。[web:22]

需要注意，微信转发、压缩或二次保存的图片可能已经丢失 EXIF 信息。因此，照片没有 GPS 并不代表没有价值，而是需要进入后续的时间、视觉和行程约束推断流程。[web:25]

## 三、推荐技术架构

建议将照片归档设计成异步处理工作流，不要让一个 Agent 一次性处理所有照片。

### 1. 照片上传与预处理

前端支持批量上传，后端为每张照片创建处理任务，并保存原始文件和基础信息：

- 文件名、文件大小、格式和哈希值。
- 上传时间。
- 图片宽高和方向。
- EXIF 信息。
- GPS 坐标。
- 拍摄时间。
- 任务状态，例如 `pending`、`processing`、`completed`、`failed`。

照片上传后，先进行文件校验、哈希去重和 EXIF 解析，再进入后续归档流程。

### 2. 有 GPS 照片处理流程

```text
照片上传
  ↓
提取 EXIF GPS
  ↓
反向地理编码
  ↓
与当前行程节点进行距离匹配
  ↓
结合拍摄时间和行程安排校验
  ↓
确定所属日期和地点
  ↓
保存照片归档结果
```

不能只根据“最近的地点”直接归档，还应综合考虑：

- 照片 GPS 与行程节点的距离。
- 照片拍摄时间与计划时间。
- 行程节点的开放时间。
- 用户当天是否安排了该地点。
- 该节点是否属于景区、商圈或大型场所。
- GPS 精度是否可靠。

例如，照片坐标距离某景点只有 300 米，但拍摄时间是凌晨 2 点，系统不应直接给出高置信度结论。

可设计如下匹配评分：

\[
Score = w_1 \times GPSScore + w_2 \times TimeScore + w_3 \times ItineraryScore
\]

其中：

- `GPSScore`：照片与行程节点之间的距离得分。
- `TimeScore`：照片拍摄时间与计划时间的匹配程度。
- `ItineraryScore`：该地点是否在用户当天行程中。

### 3. 无 GPS 照片处理流程

不建议直接询问 LLM“这张照片在哪里拍的”。更合理的做法是先根据当前行程生成候选地点，再让多模态模型在候选集合中进行判断。

```text
无 GPS 照片
  ↓
提取拍摄时间和文件名线索
  ↓
根据日期和时间筛选候选行程节点
  ↓
提取图片中的文字、地标和视觉特征
  ↓
调用多模态模型进行候选地点匹配
  ↓
综合时间、路线和视觉结果排序
  ↓
计算置信度
  ↓
自动归档或请求用户确认
```

候选地点应优先来自当前行程数据库，而不是让模型在全世界范围内猜测。例如当前行程中只有“外滩、豫园、上海博物馆、南京路步行街”，模型只需要判断照片更像这四个地点中的哪一个，准确率和可解释性都会更高。

多模态模型可以识别建筑、招牌、菜单、道路标识和景区特征，但在没有元数据时进行地理定位仍可能出现误判，尤其是普通街道、室内照片和缺乏地标信息的图片。因此，模型结果应视为候选推断，而不是确定事实。[web:6][web:8]

## 四、Agent 工作流设计

可以新增一个独立的 `PhotoOrganizerGraph`，与现有旅行规划 Agent 解耦。

### 推荐节点

```text
photo_ingest
    ↓
extract_metadata
    ↓
match_gps_photos
    ↓
build_candidate_places
    ↓
analyze_visual_content
    ↓
rank_candidate_places
    ↓
validate_result
    ↓
save_or_request_confirmation
```

### 节点职责

- `photo_ingest`：接收照片并创建处理任务。
- `extract_metadata`：解析 EXIF、GPS、拍摄时间和文件信息。
- `match_gps_photos`：处理有 GPS 的照片。
- `build_candidate_places`：从行程数据库生成候选地点。
- `analyze_visual_content`：调用视觉模型识别图片内容。
- `rank_candidate_places`：综合时间、距离、路线和视觉结果进行排序。
- `validate_result`：检查结果是否与行程安排、营业时间和路线冲突。
- `save_or_request_confirmation`：保存高置信度结果，低置信度结果进入人工确认。

该设计与现有项目“固定流程负责主路径、单 Agent 负责交互修改”的架构一致：

- 照片批量处理适合使用固定工作流。
- 用户要求“把这张照片改到另一个地点”时，可以交给现有的对话 Agent 和工具调用能力处理。
- 照片归档模块只负责识别、匹配和归档，不直接耦合行程生成逻辑。

## 五、数据库设计

### 1. `photo_assets`

用于保存照片本身及其解析结果：

```text
id
user_id
file_url
original_filename
file_hash
captured_at
latitude
longitude
exif_json
width
height
status
created_at
```

字段说明：

- `file_url`：对象存储中的原图或缩略图地址。
- `file_hash`：用于识别重复照片。
- `captured_at`：照片拍摄时间。
- `latitude`、`longitude`：EXIF 中提取的 GPS 坐标。
- `exif_json`：保存其他可能有价值的元数据。
- `status`：记录照片当前处理状态。

### 2. `photo_assignments`

用于保存照片与行程节点之间的归属关系：

```text
id
photo_id
itinerary_id
itinerary_node_id
assignment_type
confidence
evidence_json
is_confirmed
created_at
```

字段说明：

- `assignment_type`：`gps`、`time`、`vision` 或 `manual`。
- `confidence`：0 到 1 之间的置信度。
- `evidence_json`：保存距离、时间、识别文字和候选排名等依据。
- `is_confirmed`：标记结果是否经过用户确认。

如果一张照片可能属于多个地点，可以保存多个候选归属，但最终只设置一个主归属。

### 3. 可选的任务表 `photo_processing_jobs`

如果采用异步队列，建议增加任务表：

```text
id
photo_id
job_type
status
retry_count
error_message
started_at
finished_at
created_at
```

用于支持批量任务、失败重试、异常追踪和处理进度展示。

## 六、置信度与用户体验

建议将结果分为三类：

| 置信度 | 系统行为 |
|---|---|
| 0.85 以上 | 自动归档，并允许用户撤销 |
| 0.60–0.85 | 归档但标记“待确认” |
| 0.60 以下 | 不自动归档，展示候选地点 |

用户可以看到如下提示：

> 这张照片可能拍摄于“豫园”，置信度 78%。判断依据：拍摄时间为 14:20，符合当天行程；图片中识别到“豫园”文字；与当日路线匹配。
>
> [确认归档] [选择其他地点] [暂不归档]

建议保存以下信息：

- 推荐地点。
- 候选地点列表。
- 置信度。
- 判断依据。
- 是否自动归档。
- 用户是否确认或修改。

这样既能提高自动化程度，也能降低模型误判对用户数据的影响。

## 七、推荐的 MVP 范围

第一版不必直接实现复杂的全局视觉地理定位，建议按以下顺序开发：

1. 支持批量上传照片并保存文件。
2. 使用 EXIF 解析 GPS 和拍摄时间。
3. 将 GPS 照片匹配到行程节点。
4. 对无 GPS 照片按照拍摄日期和时间生成候选地点。
5. 使用多模态模型分析图片中的文字和明显地标。
6. 展示候选地点和置信度。
7. 支持用户确认、修改和撤销归档。
8. 在行程详情页展示各地点的照片。

第一版的核心价值不是准确猜出每一张照片的位置，而是帮助用户快速完成照片整理，并且保留人工修正能力。

## 八、与现有旅行规划产品融合

现有产品可以扩展为：

```text
旅行规划
├── 攻略解析
├── 行程生成
├── 路线优化
├── 事实核验
├── 行程编辑
└── 旅行照片归档
    ├── 批量上传
    ├── GPS 匹配
    ├── 无 GPS 推断
    ├── 用户确认
    └── 地点照片墙
```

在产品页面上，可以在行程详情页增加“照片”标签，按照日期和行程节点展示照片。用户也可以从某个节点直接上传照片，系统自动将该节点作为优先候选，从而减少推断范围。

后续可以继续实现：

- 根据照片自动生成每日旅行总结。
- 根据照片识别用户实际到访地点。
- 对比计划行程和实际行程。
- 自动生成旅行游记。
- 根据照片补全缺失的行程节点。
- 为景点生成“我在这里拍摄的照片”时间轴。
- 根据照片时间和位置生成旅行轨迹。

## 九、隐私与安全

照片中的 GPS 和视觉内容都涉及个人隐私。系统应提供清晰的隐私说明，并支持以下能力：

- 用户主动开启或关闭照片位置分析。
- 用户选择是否保留原图。
- 原图与缩略图分离存储。
- 对外分享时默认移除 GPS 等敏感元数据。
- 用户可以删除单张照片或全部照片。
- 用户可以删除照片处理结果和模型分析记录。
- 日志中避免记录完整图片地址和敏感坐标。
- 对视觉模型调用设置数据保留策略。

即使照片没有 EXIF，也可能通过建筑、招牌、道路标识等视觉内容推断拍摄地点，因此隐私保护不能只依赖 EXIF 清理。[web:8][web:9]

## 十、推荐开发顺序

### 阶段一：基础设施

- 增加照片对象存储。
- 实现批量上传接口。
- 建立 `photo_assets` 表。
- 实现文件校验、哈希去重和缩略图生成。

### 阶段二：GPS 自动归档

- 集成 EXIF 解析工具。
- 解析 GPS 和拍摄时间。
- 调用地理编码服务。
- 与行程节点进行距离匹配。
- 建立照片和行程节点的关联。

### 阶段三：无 GPS 候选推断

- 根据拍摄日期筛选行程。
- 根据时间筛选候选节点。
- 调用视觉模型识别文字和地标。
- 输出候选地点和置信度。

### 阶段四：人工确认与交互

- 开发待确认照片列表。
- 支持确认、修改和撤销。
- 支持用户询问“这张照片为什么归到这里”。
- 支持对话 Agent 修改照片归属。

### 阶段五：旅行记录增强

- 生成每日照片总结。
- 生成旅行游记。
- 对比计划路线与实际到访路线。
- 生成地点照片时间轴和旅行地图。

## 十一、核心结论

这个功能的核心不是单纯的“图片识别”，而是将照片、时间、地理位置、当前行程和用户反馈结合起来，形成一个受行程约束的照片归档系统。

推荐采用：

```text
EXIF/GPS 确定位置
        +
行程数据库提供候选范围
        +
视觉模型补充图片证据
        +
规则和时间线进行校验
        +
用户确认处理不确定结果
```

从工程实现角度看，最适合的方案是新增一个独立的 `PhotoOrganizerGraph`，复用现有的 FastAPI、PostgreSQL、SQLAlchemy、React、TypeScript 和 LangGraph 技术栈，并通过异步任务逐步扩展处理能力。
