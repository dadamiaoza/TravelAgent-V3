# 旅行人物相册与路线回忆地图方案

> 本文是人物识别、关系图、回忆地图的**完整愿景**。  
> **本仓库当下落地口径**见：  
> [`ai-travel-assistant/photo-archive-journal.md`](ai-travel-assistant/photo-archive-journal.md) 第 11 节。  
>  
> 冲突时以开发实录为准。已拍板：不训练自定义 YOLO 做人脸分类；人物档案挂在行程上（无登录）；回忆地图复用现有行程地图，不另做「实际轨迹」图；四个 `*Graph` 都改成普通 Job/函数。

## 一、产品定位

在“旅行照片智能归档”能力之上，增加人物识别、人物关系与地图时间线能力，形成 **旅行人物相册与路线回忆地图** 模块。

用户批量上传旅行照片后，系统可以：

1. 检测照片中的人物。
2. 将相似人物聚类为人物组。
3. 由用户为人物组命名，例如“我”“小李”“妈妈”。
4. 由用户维护人物关系，例如家人、朋友、同事、旅行同伴。
5. 将照片与人物、地点、日期、行程节点建立关联。
6. 在地图上按时间和地点顺序展示照片，形成类似游戏关卡地图的旅行回忆路线。

典型体验：

```text
起点 → 景点 A → 景点 B → 餐厅 → 景点 C → 终点
          │         │
       3 张照片   8 张照片
```

点击地图节点后，用户可以查看该地点的照片预览、出现的人物、拍摄时间、行程信息和地点说明。

## 二、总体设计原则

该功能应拆分为“人物检测、人物聚类与身份确认、照片关系管理、地图可视化”四类能力，不建议直接训练一个把每个人识别为固定类别的 YOLO 模型。

推荐原则：

1. **检测与识别分离**：YOLO 负责检测图片中是否有人以及人物位置；身份归类交由特征向量、聚类和用户确认完成。
2. **用户确认优先**：模型只给出“相似人物组”或候选身份，不应自动断言真实身份或人物关系。
3. **原图单实例存储**：照片原文件只保存一份，人物、地点、日期和行程通过关联表引用同一个 `photo_id`。
4. **缩略图优先展示**：地图和照片墙只加载缩略图；点击后加载预览图；原图仅在用户主动查看或下载时使用。
5. **真实与推断区分**：GPS 直接确认的位置、基于行程推断的位置、用户手动修改的位置应有不同标识。
6. **隐私最小化**：人脸和人物特征属于高敏感信息，应提供清晰授权、关闭识别、删除特征和撤回归类的能力。

## 三、YOLO 的职责

YOLO 适合用于 **人物检测**，不适合作为主要的人物身份分类方案。Ultralytics YOLO 支持目标检测、实例分割、姿态估计及多目标跟踪等视觉任务，可用于获得图片中人物的位置和置信度。[web:42]

### 人物检测流程

```text
原始照片
  ↓
YOLO 检测 person
  ↓
输出人物边界框（bbox）和置信度
  ↓
过滤过小、模糊、遮挡严重的人物区域
  ↓
提取可用人物区域或人脸区域
  ↓
进入人物特征提取与聚类流程
```

YOLO 检测结果可保存：

- 人物数量。
- 每个人物的边界框坐标。
- 人物检测置信度。
- 人物在画面中的位置。
- 可选的人体姿态关键点或分割区域。

### 是否需要训练 YOLO

第一版不建议立刻训练自定义 YOLO。应优先使用通用预训练 `person` 检测模型验证产品链路：

- 批量上传是否稳定。
- 人物框是否满足照片标注需求。
- 用户是否真正需要按人物浏览照片。
- 地图与时间线是否有使用价值。

只有在合照、远景、遮挡、特殊光照或特定旅行场景中检测效果持续不足时，再收集经过授权的数据进行微调训练。

## 四、人物身份归类方案

### 1. 为什么不直接训练人物分类模型

若将人物类别预先定义为“我、小王、小李”等，模型必须提前掌握每一个人的大量训练照片。该方案的问题包括：

- 新增人物通常需要重新训练或增量训练。
- 每位用户拥有完全不同的社交关系和人物集合。
- 人物外观会因光照、角度、表情、遮挡、服装和年龄变化而变化。
- 小样本条件下容易误认。
- 人脸身份处理会引入更严格的隐私和安全要求。

因此，应采用更灵活的：

```text
人物检测
  +
人脸/人物特征向量
  +
相似度匹配
  +
未知人物聚类
  +
用户命名与确认
```

### 2. 推荐识别流程

```text
人物检测
  ↓
人脸质量判断
  ↓
提取人脸或人体外观特征向量
  ↓
与已确认人物的特征向量进行相似度匹配
  ↓
将未匹配样本聚类为未知人物组
  ↓
用户确认人物组名称
  ↓
后续照片自动关联或进入待确认队列
```

系统可先向用户展示：

```text
人物组 A：出现 46 次
人物组 B：出现 31 次
人物组 C：出现 12 次
未确定人物：8 次
```

用户确认后：

```text
人物组 A = 我
人物组 B = 小王
人物组 C = 妈妈
```

对于远景、背影、侧脸、口罩、帽子遮挡或画面过于模糊的图片，应降低置信度，不应强制关联为某个确定人物。可以标记为“外观相似人物”或“未确认人物”。

## 五、人物关系设计

人物关系应作为独立的关系图维护，而不是写死到照片表中。

### `person_profiles`

```text
id
user_id
display_name
avatar_url
profile_type
status
created_at
```

建议的 `profile_type`：

- `self`：本人。
- `family`：家人。
- `friend`：朋友。
- `colleague`：同事。
- `unknown`：未确认人物。

### `person_relationships`

```text
id
user_id
source_person_id
target_person_id
relationship_type
confirmed_by_user
created_at
```

可支持的 `relationship_type`：

- 家人。
- 朋友。
- 同事。
- 伴侣。
- 旅行同伴。
- 导游。
- 其他或自定义关系。

例如：

```text
小王 — 大学同学 — 我
妈妈 — 家人 — 我
小陈 — 摄影师 — 我
```

系统可以基于用户确认的关系生成旅行总结，但不能仅凭共同出现在照片中就自动断言现实关系。

## 六、原图只存一份的设计

原始照片只保存一次；照片在不同人物、地点、日期和行程页面中出现时，均由关联表引用同一个照片资产。

```text
原始照片
   ├── 人物关联：我
   ├── 人物关联：小王
   ├── 地点关联：外滩
   ├── 行程关联：第 2 天
   └── 时间线关联：14:35
```

### `photo_assets`

```text
id
user_id
original_file_url
preview_file_url
thumbnail_file_url
file_hash
phash
captured_at
latitude
longitude
width
height
status
created_at
```

字段说明：

- `original_file_url`：原始图片存储地址。
- `preview_file_url`：适用于详情页、灯箱浏览的压缩预览图。
- `thumbnail_file_url`：适用于地图节点、列表和照片墙的缩略图。
- `file_hash`：用于判断文件是否完全相同。
- `phash`：用于判断图片是否视觉相似。
- `captured_at`：照片拍摄时间。
- `latitude`、`longitude`：照片 EXIF 中解析出的 GPS 坐标。
- `status`：照片处理状态。

### `photo_persons`

```text
id
photo_id
person_id
bbox_x
bbox_y
bbox_width
bbox_height
confidence
recognition_source
is_confirmed
```

其中：

- `photo_id` 指向唯一的原始照片。
- `person_id` 指向人物档案。
- `bbox_*` 保存人物在照片中的位置。
- `recognition_source` 可取 `manual`、`cluster`、`model`。
- `is_confirmed` 表示是否经过用户确认。

### `photo_itinerary_links`

```text
id
photo_id
itinerary_id
itinerary_node_id
assignment_type
confidence
is_confirmed
```

其中 `assignment_type` 可以是：

- `gps`：GPS 直接匹配。
- `time`：根据拍摄时间匹配。
- `vision`：根据视觉内容推断。
- `manual`：用户手动指定。

### `photo_tags`

```text
id
photo_id
tag_type
tag_value
source
```

可保存场景、食物、建筑、天气、活动等标签，为后续图片检索和游记生成提供基础。

## 七、原图、预览图与缩略图

建议将同一张照片派生为三种资源：

| 文件类型 | 主要用途 |
|---|---|
| 原图 | 下载、高清查看、长期保存 |
| 预览图 | 照片详情页、灯箱浏览、普通图片墙 |
| 缩略图 | 地图节点、照片列表、低带宽快速加载 |

地图页面不应直接加载原图，否则会导致流量、首屏加载时间和浏览器内存成本显著增加。应先展示缩略图，用户点击照片或地图节点后加载预览图，主动查看高清内容时才读取原图。

建议的逻辑目录：

```text
/photos/{user_id}/{photo_id}/original.jpg
/photos/{user_id}/{photo_id}/preview.webp
/photos/{user_id}/{photo_id}/thumbnail.webp
```

实际文件可存储于对象存储服务，数据库仅保存文件地址、尺寸、哈希和处理状态等元数据。

## 八、重复与相似照片

建议同时保存普通文件哈希和感知哈希：

```text
sha256
phash
image_embedding
```

判断逻辑：

```text
sha256 相同
→ 同一文件

sha256 不同但 pHash 距离很近
→ 疑似重复图，例如压缩、缩放或轻微编辑后的版本

内容向量相近但 pHash 不同
→ 可能是连拍、同一场景或不同拍摄角度
```

感知哈希的目标是为图片生成与视觉外观相关的指纹，因此视觉相似的图像通常会具有更接近的哈希值。[web:45][web:49]

系统不宜自动删除疑似重复照片，应在照片整理页面提示用户：

```text
发现 3 张疑似重复照片
[保留全部] [选择最佳照片] [删除选中照片]
```

## 九、地图与时间线设计

地图应设计为“旅行章节地图”或“回忆路线”，而不只是把照片随机钉在地图上。

### 地图节点类型

- 行程地点节点。
- 实际到访地点节点。
- 照片聚合节点。
- 起点和终点。
- 用户手动添加的纪念点。

### 节点数据

```text
node_id
itinerary_node_id
latitude
longitude
sequence
captured_at_start
captured_at_end
photo_count
person_count
preview_photo_url
location_source
```

其中 `location_source` 标识地点来源：

- `gps_confirmed`：由 GPS 直接确认。
- `itinerary_inferred`：由行程和时间推断。
- `manual_confirmed`：由用户确认。
- `unknown`：位置未确定。

### 路线生成流程

```text
读取已确认照片
  ↓
按拍摄时间排序
  ↓
按时间与地理位置聚合
  ↓
生成地点/照片事件节点
  ↓
连接相邻节点形成路线段
  ↓
返回地图和时间线数据
```

地图视觉建议：

- 实线：GPS 直接确认的真实路线。
- 虚线：基于行程或模型推断的路线。
- 灰色：仅有时间信息但位置未知的照片。
- 高亮节点：用户确认过的地点。
- 半透明节点：低置信度候选地点。
- 节点缩略图：展示该地点最具代表性的一张或多张照片。

如果照片没有 GPS，但已被用户确认属于某行程节点，可以在该节点展示照片，但必须标记为“关联至行程地点”，不要伪装为精确的真实拍摄坐标。

## 十、Agent 与视觉流水线

不建议把图片处理、人物检测、向量检索和路线生成全部塞入同一个 Agent。应使用多个确定性工作流处理批量任务，Agent 负责自然语言交互、解释和修改。

### `PhotoIngestGraph`

```text
upload_photo
  ↓
validate_file
  ↓
calculate_hash
  ↓
extract_exif
  ↓
generate_preview
  ↓
save_asset
```

职责：上传校验、去重、EXIF 解析、预览图生成和照片资产保存。

### `PersonAnalysisGraph`

```text
load_photo
  ↓
detect_person
  ↓
quality_filter
  ↓
extract_face_or_person_embedding
  ↓
match_existing_person
  ↓
cluster_unknown_persons
  ↓
save_person_links
```

职责：人物检测、质量过滤、特征提取、人物聚类和关联写入。

### `PhotoLocationGraph`

```text
read_gps
  ↓
match_itinerary_node
  ↓
filter_by_time
  ↓
vision_candidate_analysis
  ↓
calculate_confidence
  ↓
save_location_assignment
```

职责：GPS 位置匹配、行程候选筛选、视觉辅助推断、置信度计算和地点归档。

### `PhotoMapGraph`

```text
load_confirmed_photos
  ↓
sort_by_captured_at
  ↓
group_by_location
  ↓
build_route_segments
  ↓
return_map_timeline
```

职责：生成地图节点、路线段和按时间顺序组织的照片回忆时间线。

### Agent 职责

对话 Agent 可复用现有工具调用能力，处理：

- “查看小王在上海旅行中的照片”。
- “把这张照片标记为妈妈”。
- “为什么系统把这张照片归到外滩？”
- “把这张照片移动到第二天的豫园行程中”。
- “总结我和小王这次旅行的路线与照片”。

检测、图像压缩、向量匹配和路线排序应由确定性服务完成，避免在 Agent 上下文中堆积大量图片和中间结果。

## 十一、MVP 开发计划

### MVP-1：照片基础管理

- 批量上传照片。
- 原图单实例存储。
- 自动生成预览图和缩略图。
- 基于文件哈希的完全重复检测。
- 照片墙展示。

### MVP-2：人物检测与手动标记

- 接入预训练 YOLO 的 `person` 检测能力。
- 保存人物框、人物数量和检测置信度。
- 允许用户手动为照片人物添加标签。
- 支持人物与照片之间的多对多关联。

### MVP-3：人物聚类

- 提取人脸或人物外观特征。
- 将相似人物聚合为未知人物组。
- 用户确认人物组名称。
- 新照片自动匹配已确认人物，并保留待确认入口。

### MVP-4：地图照片路线

- 读取 EXIF GPS 和拍摄时间。
- 匹配到行程节点。
- 按时间排序并聚合节点。
- 在地图上展示节点、路径和照片缩略图。
- 支持用户确认、修改照片位置。

### MVP-5：关系和 Agent 交互

- 用户维护人物关系。
- 支持按人物、地点和日期检索照片。
- 支持对话方式修改人物和地点归属。
- 生成旅行回忆、人物同行总结和游记草稿。

## 十二、隐私与安全

人物识别、人脸特征与地理位置都属于高敏感数据。人脸图像被用于自动识别或验证时，可能构成敏感的生物识别信息；相关隐私指引通常强调处理必要性、透明告知、最小化收集和安全保护。[web:37][web:38][web:39]

建议实现以下策略：

- 默认以“人物聚类”呈现结果，不自动为陌生人确定身份。
- 用户主动命名人物组后，才建立明确人物档案。
- 提供关闭人物识别的开关，仅保留普通人物检测或地点归档。
- 尽可能保存人物特征向量与边界框，避免长期保存无必要的人脸裁剪图。
- 提供删除人物档案、特征向量、人物关联及重新匿名化的功能。
- 对儿童、陌生人和公开分享的照片提供更严格的识别与导出控制。
- 日志中避免记录完整人脸图片、原图公开地址和精确敏感坐标。
- 对外分享照片时，默认不公开内部人物关系、识别结果和特征向量。
- 向用户说明模型分析、数据保存期限和删除方式。

## 十三、核心结论

该模块的推荐技术路线如下：

```text
YOLO 人物检测
      +
人脸/人物特征向量与相似度聚类
      +
用户确认、命名与关系维护
      +
原图单实例存储与多对多关联
      +
缩略图、预览图和原图分级加载
      +
GPS/行程驱动的照片时间线和地图
      +
Agent 负责查询、解释和修改
```

最关键的三项架构决策：

1. **不要将 YOLO 当成人物身份识别模型**。YOLO 负责检测人物；身份归属使用特征向量、聚类和用户确认。
2. **照片原文件只保存一份**。人物、地点、日期和行程均通过关系表引用同一个 `photo_id`，避免重复存储。
3. **明确区分真实与推断信息**。GPS 位置、用户确认位置、行程推断位置应分别标记，保证结果可信、可解释、可修改。

该路线能以较低成本完成第一版验证，并能为后续的旅行相册、人物关系、路线回忆、实际到访分析和智能游记生成保留充足的扩展空间。
