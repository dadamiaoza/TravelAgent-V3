## 一、项目背景

旅行回来手机里有几百张照片，用户想把这些照片整理到出发前规划好的行程里（比如「Day 2 拙政园」「Day 3 西湖」），但只能靠人一张张回忆「这是哪天哪个点拍的」。

市面上产品要么做「实时轨迹记录」（旅途中一直开 GPS），要么做「行程规划」（不管照片），要么做「相册管理」（不懂行程）。

**本项目要做的是：旅行结束后，把照片自动挂到已经规划好的行程节点上，拿不准的让用户确认。**

---

## 二、目标用户

- 20–35 岁自由行用户（学生、情侣、朋友小团体）
- 会用 AI 或 App 提前规划行程的人
- 旅行回来照片多、懒得一张张整理
- 不需要登录体系，行程是匿名的（和 TravelAgent-V3 产品一致）

---

## 三、用户痛点

1. **照片太多，整理太累**：一张张回忆「这是哪天哪个点拍的」成本高
2. **微信转发丢 EXIF**：GPS 和拍摄时间都可能没有；文件下载时间不是游玩时间
3. **现有产品要么费电要么太慢**：实时轨迹要求旅途中一直开定位；手动加照片效率低
4. **相册 App 不懂行程**：只知道时间和地点，不知道「这是行程里计划的那个点」

---

## 四、产品定位

> **「旅行照片智能归档」是现有旅行规划产品的一个模块，不是新的旅行规划 Agent。**

**三不做原则（第一刀仍成立）：**

1. 不做行程生成
2. 不重新排路
3. **不静默**往计划行程里加点（不改 `itinerary_items` 的顺序和节点集合）

**第一刀只做一件事：** 把照片挂到已经规划好的行程节点上。

**下一刀（PC1–PC3，见执行计划）：** 计划外 GPS 聚类 → 用户确认 → 写入**实际到访**（`visit_stops`）。回忆 Tab 展示足迹；不是第二份可编辑行程。

## 五、核心使用场景

### 场景 1：旅行结束后批量归档

```
用户打开某次行程 
  → 批量上传照片 
  → 系统自动匹配到行程节点 
  → 高置信度的自动挂上，拿不准的列出来让用户确认 
  → 每个节点下能看到自己的照片墙
```

### 场景 2：单张照片改归属

```
用户发现某张照片挂错了 
  → 点「改挂」 
  → 选另一个节点 
  → 完成
```

### 场景 3：地图回忆线

```
用户打开回忆 Tab
  → 看到计划点（淡底）和已确认实际停留（实心钉）
  → 点钉看该地点的照片墙
```

### 场景 4：计划外地点（下一刀，第一刀未做）

```
用户上传的照片离所有计划节点都很远
  → 系统按 GPS 聚成一簇，逆地理给出建议地名
  → 用户确认「这批就是这里」→ 实际到访钉出现在回忆页
  → 计划行程列表不变
```

## 六、MVP 功能清单

| 编号 | 功能 | 说明 |
|------|------|------|
| F1 | 批量上传照片 | 行程详情页上传，支持多张，文件先存本地磁盘 |
| F2 | 解析 EXIF | 读 GPS、拍摄时间、宽高、生成文件哈希（去重） |
| F3 | GPS 匹配 | 有 GPS 的照片：按距离 + 拍摄时间 + 是否在当天行程里打分，匹配到节点 |
| F4 | 无 GPS、有拍摄时间 | 列出当天候选节点，不自动定论 |
| F4b | 微信/下载图（无 GPS 且无拍摄时间） | 进待确认；**不用**下载时间；按天展示节点供改挂；从某节点「上传到这里」视为用户已指定地点 |
| F5 | 待确认列表 | 低置信度或类型 B/C 的照片进待确认，用户可确认、改挂、撤销；支持按天批量改挂 |
| F6 | 节点照片墙 | 行程节点下展示已归档照片（预览图） |
| F7 | 地图缩略图 | 现有行程地图的 Marker 上显示缩略图和张数 |
| F8 | 去重 | 同一行程内相同文件哈希的照片不存第二份原图 |
| F9 | 生成预览图和缩略图 | 上传时自动生成，用于照片墙和地图 Marker |
| F10 | 保存判断依据 | 记录距离、时间差、用了哪条规则，方便解释「为什么挂在这里」 |

## 七、暂不实现的功能

| 功能 | 原因 |
|------|------|
| 让 LLM 直接回答「这张在哪拍的」 | 没有约束会胡说，地点匹配是计算不是 AI |
| 登录 / 用户账号 | V3 不做登录，照片挂在行程上（`trip_id`） |
| 对象存储（S3/MinIO） | 第一期本地 `uploads/` 足够演示 |
| 多模态视觉识别 / 人脸识别 | 贵、慢、隐私敏感，不是最小闭环 |
| 按照片**静默**补计划节点 / 重排计划 | 会反向改行程；确认后的实际到访写 `visit_stops`，见执行计划 PC2 |
| 第二份可编辑「真实行程」 | 和计划抢真源 |
| 生成游记 / 轨迹回放 | 单独开需求，不是第一刀也不是 PC1–PC3 |
| Redis / Celery 异步队列 | 第一期先同步跑通，再拆 Worker |

## 八、用户操作流程

### 主流程（批量归档）

1. 用户打开行程详情页
2. 点「上传照片」→ 选多张照片
3. 系统解析 EXIF → 打分匹配 → 高置信度自动挂上，低置信度进待确认
4. 用户在节点照片墙看到已归档照片
5. 有待确认列表 → 用户确认或改挂

### 分支流程（改归属）

1. 用户在照片墙点某张照片 → 点「改挂」
2. 选另一个节点 → 完成

### 分支流程（回忆）

1. 用户打开回忆 Tab（路由 `/map`）
2. 看到计划淡底和已确认实际钉（PC3；当前代码仍只有计划钉）
3. 点钉 → 看该地点照片墙

## 十、每个页面的主要功能

### 行程详情页

- 展示行程节点列表（已有）
- 新增「照片」区域：上传按钮、已归档照片总数、待确认入口
- 每个节点卡片下展示该节点的照片墙（缩略图网格）

### 照片上传页

- 选多张照片（支持相机相册）
- 显示上传进度
- 上传完成后跳转到待确认列表（如果有）

### 待确认列表页

- 列出所有待确认照片（缩略图 + 候选节点列表）
- 每张卡片：确认、改挂、撤销
- 支持批量确认

### 节点照片墙（内嵌）

- 网格展示该节点的照片（预览图）
- 点照片看大图（灯箱）
- 支持改挂、撤销

### 回忆页（已有壳，PC3 换数据）

- 计划层淡底（可关）+ 已确认实际停留实心钉
- 点钉 → 该地点照片墙
- 只读：不在此页改计划节点

## 十一、数据对象设计

### `photo_assets`（一张照片一行）

| 字段 | 含义 |
|------|------|
| `id` | UUID |
| `trip_id` | 属于哪次行程（级联删除） |
| `file_path` | 原图相对路径 |
| `preview_path` | 预览图路径（可空） |
| `thumbnail_path` | 缩略图路径（可空） |
| `original_filename` | 用户看到的文件名 |
| `file_hash` | SHA-256，同一行程内去重 |
| `captured_at` | EXIF 拍摄时间（可空） |
| `latitude` / `longitude` | EXIF GPS（可空） |
| `exif_json` | 其余元数据（可空） |
| `width` / `height` | 像素 |
| `status` | `pending` / `processing` / `completed` / `failed` |
| `created_at` | 上传时间 |

### `photo_assignments`（照片 ↔ 节点）

| 字段 | 含义 |
|------|------|
| `id` | UUID |
| `photo_id` | 哪张照片 |
| `item_id` | 哪个行程节点（可空，待确认时） |
| `assignment_type` | `gps` / `time` / `manual` |
| `confidence` | 0–1 |
| `evidence_json` | 距离米数、时间差、候选排名、规则名 |
| `is_confirmed` | 用户是否点过确认 |
| `is_primary` | 一张照片只允许一个主归属 |

### `photo_jobs`（一批上传）

| 字段 | 含义 |
|------|------|
| `id` | UUID |
| `trip_id` | 哪次行程 |
| `status` | `pending` / `processing` / `completed` / `failed` |
| `progress` | 0–100 |
| `payload` | 这批处理哪些 `photo_id` |
| `error` | 错误信息（可空） |
| `created_at` / `updated_at` | 时间戳 |

## 十二、验收标准

### 功能验收

自动化（pytest，用合成数据）：

1. 已知距离很近且时间落在节点窗口内 → 分数 ≥ 0.85，自动挂上  
2. 无 GPS、仅有拍摄时间 → 不自动挂，候选为当天节点  
3. 无 GPS、无拍摄时间（模拟微信图）→ 不自动挂，`captured_at` 为空，**不**用文件 mtime 填时间  
4. 同一 `file_hash` 第二次上传 → 不写第二份原图  
5. WGS-84 → GCJ-02 转换与已知点对一致  

演示脚本（真机照片，人工看，不写进 CI 断言「挂对了」）：

5. 上传约 10 张带 GPS 的旅行照，多数应落到正确节点；挂错的能改挂  
6. 地图 Marker 显示缩略图和张数，点开能看该节点照片墙  
7. 待确认：确认 / 改挂 / 撤销后照片墙更新

### 性能验收

1. 批量上传 50 张照片 → 处理时间 < 2 分钟
2. 单张照片解析 EXIF → < 1 秒
3. 打分匹配 100 张照片 × 20 个节点 → < 5 秒

### 体验验收

1. 上传过程有进度条
2. 待确认列表清晰（缩略图 + 候选节点）
3. 改挂操作简单（两步内完成）
4. 地图缩略图不遮挡 Marker 核心信息

### 下一刀（PC1–PC3，优先）

见 [计划与回忆-执行计划.md](./计划与回忆-执行计划.md)：Tab 文案、聚类确认、回忆双层地图。

### 短期（1–2 个月）

1. 异步 Worker（`photo_jobs` 拆成独立服务）
2. 对象存储（S3/MinIO）替换本地磁盘
3. 照片分享（剥 EXIF 后分享）
4. 视觉识别（多模态模型在「当天候选」里选择，可关闭）

### 中期（3–6 个月）

1. 对话改归属（Trip Assistant 工具：「把这张改到拙政园」）
2. 人物检测（预训练 YOLO 只检测 `person` 框，用户给框起名）
3. 人物聚类（特征向量 + 用户命名）
4. 行程内人物关系（不建账号级社交图）

### 长期（6 个月+）

1. 对比「哪些计划点没有实心钉」（派生视图，仍不删计划节点）
2. 游记生成（基于照片和行程）
3. 轨迹回放（按时间顺序播放照片）

## 附录 A：给新手的提醒

### 1. 坐标系偏移（最大的技术坑）

EXIF GPS 是 WGS-84，高德地图用 GCJ-02，直接算距离会偏 200–600 米——上传后必须先做坐标转换再算分。

**建议：** 在 PA2（EXIF 解析）阶段就加入坐标转换逻辑，并写单元测试验证。

### 2. EXIF 时间没有时区

跨国旅行或相机时间没校准时，要按行程目的地时区解释。

**建议：** 在打分函数里增加时区校正参数，默认使用行程目的地时区。

### 3. 不要一上来就搞 AI 看图

第一版只做 GPS + 时间匹配，视觉识别是 PB1 以后的事。

### 4. 去重很重要

同一行程内相同文件哈希的照片不存第二份，节省空间也避免混乱。
