# AI 旅行规划助手 V3：产品需求

> 日期：2026-09-04  
> 定位：把已跑通的工程收成**合格抄作业产品**，并在**生成后的协作**里做一个带工具的行程助手。  
> 与 V1/V2 关系：不重写产品方向。V1 定「可执行、可信、可改」；V2 定搜索抓取与解析增强。V3 纠正「编排用在哪」：生成走固定任务图，协作走一个 Trip Assistant（工具自选）。冲突以本文为准。  
> 实现对照：仓库当前行为见 `.ad/retrospect/knowledge-map.md` §0。

---

## 1. 一句话

年轻自由行用户带着攻略或一句话进来，得到一份**按天可改的行程**；贵步骤由用户确认，路时和任务状态由代码保证，模型只出现在不确定判断上。

不是：一个万能聊天框里四个专家互相移交，从零发明一份攻略。

---

## 2. 目标用户与场景

| | 内容 |
|--|--|
| 用户 | 学生 / 朋友 / 情侣自由行（与 V1 一致） |
| 高频行为 | 小红书抄作业 → 按自己的天数和必去点改 |
| 痛点 | 多篇攻略手工拼接；纯聊天生成幻觉、过时、不能改 |
| 首发形态 | Web。不做 App、不做登录体系（可匿名行程） |

核心场景三条，必须都能独立演示：

1. **抄作业：** 贴文本 → 候选列表 → 勾选 → 排路成行程。  
2. **从零：** 目的地 + 日期 → 一次规划选点 → 同一套排路。  
3. **改行程：** 对话或表单改节点；AI 只出建议，点采纳才写库。

---

## 3. 北极星与合格标准

北极星：**抄完并能改，且失败看得见。**

合格（P1 结束必须同时成立）：

1. 攻略勾选后**不再**先跑一遍从零生成。  
2. 从零生成是一次规划 + 函数排路，阶段可回查。  
3. 聊天与表单修改都经 Delta / 编辑接口，Agent 不写库。  
4. 生成结束或关键修改后，用户能看见时效风险（允许降级，不许静默当没发生）。  
5. 文档与简历不把未接前端的 Supervisor 写成产品主路径。

---

## 4. 两条入口，一份候选，一个排路器

```
入口 A 源材料 → 解析 → 候选列表 → 用户勾选 ─┐
入口 B 短澄清 → 规划 Agent 一次选点 ─────────┼→ 路线优化（函数）→ 行程
入口 C 代搜链接 → 搜索确认 → 抓取 → 解析 ───┘      （第三种填候选，非首页默认）
```

A 不是 B 的内部步骤。B 的规划 Agent 只在「没有候选」时出现。

---

## 5. 功能需求

### 5.1 生成任务图（编排：固定依赖）

一次 `GenerationJob` 执行三个节点：

| 节点 | 用户感知 | 规则 |
|------|----------|------|
| **fill** | 「正在准备景点」 | 有已勾选候选 → 按 `day_index` 拼 JSON，不调规划 Agent；无候选 → `itinerary_gen` 最多搜一次景点池 |
| **route** | 「正在补路线」 | 永远 `optimize_itinerary()` |
| **verify** | 「正在核对开放时间/天气」 | 规则引擎 + 天气/开放时间；失败只打风险，不回滚已排路线 |

Job 五态、SKIP LOCKED、`run_token`、SSE 通知 + GET 回查：沿用现实现，不新开队列中间件。

### 5.2 协作助手（编排：一个 Agent + 工具）

行程存在之后，侧栏才是协作主场。不拆编辑/核验/解析三个 Agent，也不先做意图分类器再 `if/elif` 硬路由。一个 **Trip Assistant** 读当前行程，自己决定调用 0/1/多个工具（实现为 Service 函数）。

| 用户可能说 | 典型工具 | 产出 |
|------------|----------|------|
| 把灵隐寺换成 ent / 删掉雷峰塔 | `propose_delta` | `ItineraryDelta`（add/update/delete/reorder） |
| 我不喜欢第二天，帮我重排当天顺序 | `propose_delta`（reorder）+ 采纳后 `reoptimize_day` | 当天节点重排，不新发明一份行程 |
| 第二天会不会下雨 / 周一开馆吗 | `check_facts` | 风险说明；高风险可附「建议删除/改期」Delta |
| 闭馆是真的吗，要不要删 | `check_facts` + `propose_delta`（一轮可两个） | 说明 + 可选 delete Delta |
| 按这段攻略加点 | `parse_guide` | 实体 → add Delta，仍需用户采纳 |

写库策略（对话旁模式，类似 Claude Code）：

- **只提议**（默认，现状）：不得调 `apply_delta`；前端展示建议，用户点采纳后走已有 `POST /trips/{id}/deltas/apply`。  
- **授权后自动采纳**：本会话允许调 `apply_delta`，前端立刻刷新。不要做成永远自动写。

约束：

- 建议协议保持现有 `reply` + `suggestions: ItineraryDelta[]`，不另搞 `remove_item` JSON，也不为聊天新增 `DELETE /items/{id}`。  
- **禁止**在对话里调用 `itinerary_gen` 重做整份行程。整份重来走「重新生成」+ Job。当天「重排」是已有节点的 reorder + `reoptimize_day`，不是再规划一套景点。  
- **禁止**路线专家 Agent；采纳 add/reorder 后已有 `reoptimize_day`。  
- 不把 `POST /api/v1/chat` 无行程上下文 Supervisor 接到行程页。

### 5.3 行程编辑（已有，保持）

节点增删改排、同天重算、地图连线。锁定节点（`is_locked`）在重排时保留。

### 5.4 明确不做（V3 窗口内）

登录 / RBAC、订票、社区、多人实时编辑、Redis/Celery/K8s、把 Supervisor 当首页、图片攻略（无多模态验收）、把代搜做成首页默认、假 RAG 评测集。

V2 的搜索确认（入口 C）排在 P2 协作稳定之后，作为填候选的增强，不替代 A 的粘贴。

---

## 6. 体验原则

1. 贵步骤有人控：勾选、采纳、搜索确认。  
2. 进度说人话：fill / route / verify，可展开阶段。  
3. 模型失败可见：JSON 坏了可重试；Trip 不存在则失败，不卡在转圈。  
4. 降级不装真：高德失败用估算时，UI 不标「已核实」。

---

## 7. 成功演示脚本（验收）

1. 首页：杭州 3 日 → 数分钟内出行程，阶段能看到规划与排路。  
2. 攻略页：贴一篇文本 → 勾选 5 个点 → **创建行程时不先生成一份无关行程** → 打开后节点来自勾选。  
3. 行程页：说「灵隐寺周一开门吗」→ 看到核验回复；说「删掉雷峰塔」→ 出现 Delta → 采纳后列表与地图变。  
4. 刷新生成中页面：仍能看到 Job 状态。  
5. 杀 Worker 再拉起：任务能重试或失败，不无声挂死。

---

## 8. 简历与文档口径

可写：职责拆分（解析 / 规划 / 核验作为**工具/服务**，不是三个独立 Agent）；生成用 Job 任务图；行程侧栏一个 Trip Assistant 自选工具；默认只提议、可切授权后自动采纳；Delta 写库。

不可写：产品主路径是 Supervisor 动态调度四个专家完成规划；也不可写侧栏是多 Agent 互相移交——协作是**一个助手 + 工具**，且说的是**改行程**不是**首次生成**。
