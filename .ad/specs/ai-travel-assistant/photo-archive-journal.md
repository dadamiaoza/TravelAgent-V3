## 0. 读之前先记住三句话

1. **照片归档不是让模型猜地点。** 有 GPS 就用距离和时间打分；计划外用聚类 + 逆地理；拿不准就让用户点。
2. **它是行程上的一个模块，不是新的旅行规划 Agent。** 不排路、不重新生成行程、**不静默**往计划里加点。用户确认后的实际到访写在 `visit_stops`，和计划是两份真源。
3. **批量处理是固定工作流（Job），对话改归属才是 Agent。** 和现在「生成用 Job、聊天用助手」同一套分工。

## 2. 需求分析

### 2.1 要解决的问题

用户旅行结束后（或行程已经规划好之后），手头有几十到上百张照片。有的手机原图带 GPS，有的是微信转发后丢了 EXIF。现在只能靠人一张张想「这是哪天、哪个点拍的」。

产品要做的是：**把照片挂到计划节点上；挂不上的用 GPS 聚类提出实际停留，等人确认**。不是再发明一份可编辑行程，也不是让模型编地点。

典型路径：

```
用户打开某次行程 → 批量上传照片
  → 系统只从 EXIF 读 GPS / 拍摄时间（不用文件下载时间）
  → 有 GPS：和当天计划节点比距离 + 时间，高置信度可自动挂
  → 挂不上计划点：聚类 + 逆地理 → 「建议停留」，确认后写入实际到访
  → 无 GPS、但有拍摄时间：列出当天候选，不自动定论
  → 微信等下载图：进待确认，不假装知道地点
  → 用户确认 / 改挂 / 或从某个节点「上传到这里」
  → 行程 Tab 看计划照片墙；回忆 Tab 看实际足迹钉
```

### 2.2 目标用户

和 V3 一致：年轻自由行（学生 / 朋友 / 情侣）。没有登录体系，行程是匿名的，照片也挂在**那一次行程**上，不挂「账号」。

### 2.3 本期做 / 不做

**本期做（第一刀，对应产品方案阶段一 + 二 + 很薄的确认界面）：**

1. 行程详情页批量上传照片，文件先存在本机磁盘。  
2. 解析 EXIF：GPS、拍摄时间、宽高、哈希去重。  
3. 有 GPS 的照片：按距离 + 拍摄时间 + 「是否在当天行程里」打分，匹配到 `itinerary_items`。  
4. 没有 GPS 的照片：若 EXIF 里有拍摄时间，列出当天候选节点，**不自动定论**。  
5. **微信等下载图（常见：GPS 和拍摄时间都没有）**：不把下载时间当成游玩时间；进待确认。用户可从某个节点「上传到这里」（视为已指定地点），或在待确认里按天挑选。同一批上传里若邻图已 GPS 命中某节点，只作为低置信度候选，绝不自动挂。  
6. 行程节点下展示已归档照片；有「待确认」列表；用户可以确认、改挂到另一个节点、撤销。  
7. 保存判断依据（距离、时间差、用了哪条规则），方便以后解释「为什么挂在这里」。  
8. 上传时生成预览图和缩略图；**现有行程地图**上按节点顺序展示缩略图（关卡式回忆线）。第一刀不另画实际轨迹；下一刀（PC2–PC3）用确认后的 `visit_stops` 另画一层。

**第一刀明确不做（PA1–PA7，已落地）：**

| 不做 | 原因 |
|------|------|
| 让 LLM 直接回答「这张在哪拍的」 | 没有约束会胡说；和排路一样，地点匹配是计算 |
| LangGraph `PhotoOrganizerGraph` | 步骤顺序固定，应写成 Job Worker，不要再包一层 Agent |
| 登录 / `user_id` 作为照片主人 | V3 不做登录；照片外键是 `trip_id` |
| 复用 `generation_jobs` 表 | 该表限制「一个行程同时只能有一个进行中的生成任务」，照片批处理会和生成抢锁 |
| Redis / Celery / 对象存储（S3） | 第一期本机 `uploads/` 足够演示；上线再换 |
| 多模态视觉识别 / 训练 YOLO 认人 | 第一期没有视觉验收；认人是另一条流水线，见第 11 节 |
| **静默**按照片补计划节点 / 用照片重排 `seq` | 会反向改计划，和「归档不耦合生成」冲突 |
| 第二份可编辑「真实行程」Day 列表 | 和计划抢真源；聊天和排路会乱 |
| 把 Supervisor 或 `POST /api/v1/chat` 接到相册 | 改归属以后走现有 Trip Assistant 工具，现在连工具都先不做 |

**下一刀要做（PC1–PC3，文档已拍板、代码未做）：** GPS 聚类 + 逆地理 → 用户确认 → `visit_stops`；回忆地图计划淡底 + 实际实心钉。详见 [执行计划](../计划与回忆-执行计划.md)。

### 2.4 和现有产品怎么拼

```
旅行规划（已有）
├── 攻略解析
├── 行程生成（Job：fill → route → verify）
├── 路线优化（函数 optimize_itinerary，不是 Agent）
├── 事实核验
├── 行程编辑 + 侧栏 Trip Assistant
└── 旅行照片归档（新模块，挂在行程上）
    ├── 批量上传
    ├── GPS + 时间匹配
    ├── 待确认 / 改挂
    └── 节点照片墙
```

页面入口：行程 Tab 底部上传 / 待确认；节点「上传到这里」。回忆 Tab（路由仍 `/map`）看足迹，不在回忆页改计划。

## 3. 方案设计（为什么这么做）

### 3.1 总原则：分层，不要让模型当地理学家

和排路相同：

| 事情 | 谁做 | 为什么 |
|------|------|--------|
| 读 EXIF、算距离、比时间 | Python | 每次都必须发生，结果可测 |
| 候选地点从哪来 | 行程数据库 | 模型不准满世界猜 |
| 高/中/低置信度怎么处理 | 写死的阈值 | 用户能预期系统行为 |
| 「把这张改到拙政园」 | 以后的 Trip Assistant 工具 | 用户一句话，工具集合事先不知道 |
| 视觉模型看图 | **第一期不做**；以后只在「当天候选」里选 | 贵、慢、隐私敏感，且不是最小闭环 |

产品方案里的公式仍然适用：

```
Score = w1 × GPSScore + w2 × TimeScore + w3 × ItineraryScore
```

- `GPSScore`：照片坐标到节点 `lat/lng` 的距离（已有地理编码结果）。  
- `TimeScore`：拍摄时间 vs 节点 `start_time` / `end_time`（没有拍摄时间则该项为 0，不能假装很准）。  
- `ItineraryScore`：该节点是否属于拍摄日对应的那一天。

不能只取「最近的一个点」。例如距离拙政园 300 米、但拍摄时间是凌晨 2 点，不应高置信度自动归档。

**匹配前必须先对齐坐标系。** 行程节点的 `lat/lng` 来自高德地理编码，是 **GCJ-02**。手机 EXIF 里的 GPS 是 **WGS-84**。中国境内直接拿去算距离会偏大约 200–600 米，高置信度会整批挂错。做法：

- `photo_assets.latitude/longitude` **原样保存 EXIF（WGS-84）**，方便以后导出。  
- `photo_match` 打分时把照片坐标转成 GCJ-02，再和节点比。  
- 转换函数必须有单元测试（已知点对），不要在前端或地图展示层偷偷转两次。

**拍摄时间往往没有时区。** EXIF `DateTimeOriginal` 一般是相机当地时间、不带 offset。第一期按行程目的地解释：国内行程默认 `Asia/Shanghai`；和节点 `date + start_time` 比的是「行程日历上的钟点」，不是 UTC。相机没对时导致差很多小时的，分数会低，进待确认——这是正确行为，不要用 LLM 猜时区。

### 3.1.1 三类照片（微信图是第三类，不是「无 GPS」的特例）

从微信、QQ、浏览器「另存为」下来的图，压缩和转发后 **EXIF 经常被剥光**：没有 GPS，也没有 `DateTimeOriginal`。文件的修改时间、微信 `mmexport` 文件名里的数字，都是**保存/下载时间**，不是游玩时间。当成拍摄时间会把整批照片挂到「今天下载」的那天。

| 类型 | 有什么 | 系统做什么 | 不做什么 |
|------|--------|------------|----------|
| A 原图 | GPS，时间可有可无 | 转 GCJ-02 后打分；高置信度可自动挂 | 只按最近邻、不管凌晨 |
| B 部分 EXIF | 无 GPS，有拍摄时间 | 当天节点作候选，**不自动挂** | 不假装知道是哪一个景点 |
| C 下载图 | 两者都没有（微信常态） | 进待确认；候选按「天」分组列出整次行程节点 | **不用**文件系统时间、下载时间、`mmexport` 时间戳当 `captured_at` |

类型 C 怎么让人省事（第一期，仍然不是认地点）：

1. **从某个行程节点点「上传到这里」**：用户已经指定地点，记 `assignment_type=manual`，可直接挂上（这是人控，不是模型猜）。  
2. **在行程页整批上传**：全部进待确认；界面按 Day 1 / Day 2 选节点，支持多张一起改挂。  
3. **同批邻图提示（可选、低置信度）**：同一 `photo_job` 里已有类型 A 自动挂到「拙政园」的，旁边的类型 C 可以把拙政园列为第一候选，分数封顶低于自动归档线（例如 ≤ 0.55）。用户仍要点确认。  
4. 视觉认地标、LLM 看图：**不做**，见第 11 节 / PB。

`captured_at` 只允许来自 EXIF（`DateTimeOriginal` / GPS 时间）。解析不到就保持 `NULL`，不要回填 `created_at`。

建议阈值（实现时可微调，改阈值必须同步改本节和测试）：

| 分数 | 系统行为 |
|------|----------|
| ≥ 0.85 | 自动挂到该节点，允许撤销 |
| 0.60–0.85 | 挂上但标「待确认」 |
| < 0.60 | 不自动挂，只展示候选 |

### 3.2 为什么用 Job，不用 PhotoOrganizerGraph

现有生成路径已经证明：把固定步骤包成 Agent 会变慢、变难测。照片处理更是固定顺序：

```
保存文件 → 解析 EXIF → GPS 匹配 →（可选）无 GPS 候选 → 写 assignment
```

所以：

- 一次批量上传 → 创建一个 **`photo_jobs` 批次**（或「每张照片一个子任务」）。  
- Worker 按阶段推进，前端用 SSE 或轮询看进度（照抄 `generation_jobs` 的体验，但**另开表**）。  
- 不要新建 LangGraph 图。

### 3.3 数据挂在行程上，不挂用户上

当前 `trips.user_id` 可空，产品是匿名行程。照片表设计：

**`photo_assets`（一张照片一行）**

| 字段 | 含义 |
|------|------|
| `id` | UUID |
| `trip_id` | 属于哪次行程（级联删除） |
| `file_path` | 原图相对路径；以后改对象存储只换存储层 |
| `preview_path` | 详情/灯箱用的预览图，可空（生成前为空） |
| `thumbnail_path` | 地图钉、列表用的缩略图，可空 |
| `original_filename` | 用户看到的文件名 |
| `file_hash` | SHA-256，同一行程内去重；相同则**不存第二份原图** |
| `captured_at` | EXIF 拍摄时间，可空 |
| `latitude` / `longitude` | EXIF GPS，可空 |
| `exif_json` | 其余元数据，可空 |
| `width` / `height` | 像素 |
| `status` | `pending` / `processing` / `completed` / `failed` |
| `created_at` | 上传时间 |

**`photo_assignments`（照片 ↔ 节点）**

| 字段 | 含义 |
|------|------|
| `id` | UUID |
| `photo_id` | 哪张照片 |
| `item_id` | 哪个 `itinerary_items.id`，待确认时可空 |
| `assignment_type` | `gps` / `time` / `manual`（以后才有 `vision`） |
| `confidence` | 0–1 |
| `evidence_json` | 距离米数、时间差、候选排名、规则名 |
| `is_confirmed` | 用户是否点过确认 |
| `is_primary` | 一张照片只允许一个主归属 |

**`photo_jobs`（一批上传）**

不要复用 `generation_jobs`。字段可参考生成任务：`trip_id`、`status`、`progress`、`attempts`、`stages`、`error`、时间戳。一批里处理哪些 `photo_id` 放在 `payload` 里。

### 3.4 文件存在哪

第一期：仓库外的本地目录，例如 `src/backend/uploads/`（必须进 `.gitignore`）。  
Docker 里只有 Postgres，不加 MinIO。演示 200 张 JPEG 可以接受；真要上线再加对象存储。

### 3.5 和现有代码怎么接（给实现的人看）

已经能复用、不必重写的：

| 现有能力 | 照片模块怎么用 |
|----------|----------------|
| `itinerary_items.lat/lng` | GPS 距离 |
| `itinerary_days.date` + `items.start_time/end_time` | 时间窗 |
| `GenerationJob` + Worker + SSE | **抄形态**，新建 `photo_jobs` |
| `TripPage` / `ItineraryItemCard` | 照片墙和「待确认」UI 的宿主 |
| 高德 `geocode_poi` | 节点已经有坐标；挂到**计划节点**不必再逆地理。计划外簇的地名才需要新建 `regeo`（PC2） |

需要新建、现在仓库里没有的：

- 上传 API、multipart、MIME/大小校验  
- EXIF 解析（Python 侧，如 `pillow` + 读 GPS；或调用 exif 库）  
- 三张表的 Alembic 迁移（当前最新迁移是 `0017`，下一号是 `0018`）  
- 打分函数（纯 Python，必须有单元测试）  
- 行程页照片 UI  

### 3.6 隐私（第一期最小集）

第一期至少做到：

1. 界面说明：照片只用于匹配当前行程，不拿去训练。  
2. 可删除单张照片（文件 + 库记录）。  
3. 日志不打印完整 GPS。  

关闭视觉分析：第一期没有视觉，这条等阶段三再做。分享时剥 EXIF：第一期没有分享，不做。

## 11. 人物相册与回忆地图：当下合理方案

完整愿景：[旅行人物相册与路线回忆地图方案.md](../旅行人物相册与路线回忆地图方案.md)。  
下面只回答：**以这个仓库现在的能力，先做什么才合理。**

### 11.1 和「训练一个 YOLO 认人」的关系

**不要训练自定义 YOLO 来当人物分类器。** 愿景文档第三节已经写对了，这里再钉死一次。

| 做法 | 当下是否做 | 原因 |
|------|------------|------|
| 自己收集数据微调 YOLO，类别 = 我/小李/妈妈 | **不做** | 每个人的旅伴都不同，加一个人就要重训；小样本会认错；人脸是高敏感生物信息；本项目还没有登录和授权流 |
| 用预训练 YOLO 只检测 `person` 框 | **推迟到 PB1** | 不认身份，只回答「图里有几个人、在哪」；要等照片上传稳定之后再加 PyTorch/ONNX 依赖 |
| 人脸/人体向量 + 聚类，用户给组起名 | **推迟到 PB2** | 身份来自用户命名，不是模型类别 |
| 用户指定人物关系 | **推迟到 PB3** | 没有稳定的「人物档案」就没有关系可填；本项目无账号，关系只能挂在**这一次行程**上 |

「所有照片只存一份，不同人用指针指向原图」——这个**现在就按这个建表**。`photo_assets` 一行一文件；以后 `photo_persons` 只存 `photo_id` + 框 + 人物档案 id，不复制 JPEG。

### 11.2 回忆地图：同一张图、两层数据

仓库里已经有 `TripMap`：按天、按 `seq` 打 Marker，节点之间有高德折线。这是**计划层**。

第一刀（已完成）：计划 Marker 上挂缩略图和张数；无 GPS 但用户确认属于该节点的照片出现在同一钉上，不伪装成精确拍摄坐标。

下一刀（PC2–PC3）：

```
计划层（淡底，可关）
    └── itinerary_items + 已有 route_polyline
实际层（实心钉）
    └── 已归档到计划点的照片（仍用计划坐标）
    └── 用户确认过的 visit_stops（簇中心）
建议层（待确认，不是实心关卡）
    └── status=suggested 的簇，不画成正式足迹
```

明确不做：

- 不另做一张可编辑 Day 列表当「真实行程」。  
- 不把无确认的推断钉成实心关卡。  
- 不用照片顺序覆盖计划 `seq` / 规划折线。实际连线另画一层。

视觉上仍像关卡图：实现上还是现有 `TripMap`，不是新地图引擎。

### 11.3 表怎么留扩展、但第一期不建人物表

第一期（PA1）就要有的：

- `photo_assets`：原图 + `preview_path` + `thumbnail_path` + `file_hash` + `trip_id`  
- `photo_assignments`：照片 → 行程节点（多对一主归属）  
- `photo_jobs`

第一期**不要建**、等 PB1 再加：

- `person_profiles`：必须带 `trip_id`（不要 `user_id`，没有登录）  
- `photo_persons`：`photo_id` 指针 + bbox + `person_id`（可空，表示「检出人但未命名」）  
- `person_relationships`：两端都是本行程的 `person_profiles`

这样原图始终一份；「小李的相册」只是过滤 `photo_persons`，不是拷贝文件。

### 11.4 工作流：仍然不要四个 Graph

愿景里的 `PhotoIngestGraph` / `PersonAnalysisGraph` / `PhotoLocationGraph` / `PhotoMapGraph` 都是固定顺序，全部做成 **Service 函数或 `photo_jobs` 阶段**。

对话 Agent 仍然只负责以后的：「这张是妈妈」「为什么挂在外滩」。批量检测、压缩、打分、按 `seq` 拼地图数据都不进 LLM。

### 11.5 当下执行顺序（只这一条）

```
第一刀已完成
  PA1–PA7：上传、EXIF、GPS 匹配、照片墙、行程/地图拆分

现在（文档已冻结，等实现）
  PC1–PC3：行程|回忆 Tab、聚类确认、回忆双层钉

照片墙 + 实际停留能用之后（另开一小段）
  PB1：预训练 person 检测 + 用户给框起名

始终不做，直到有明确失败案例和授权数据
  自定义 YOLO 训练、账号级人物图谱、静默按照片改计划
```

验收第一刀成功的标志：上传带 GPS 的照片，地图上按**计划**顺序能点开各地点缩略图；同一文件不会存两份原图。  
验收下一刀：计划外 GPS 簇确认后，回忆页出现新钉，行程节点列表不变。
