## S9：bug 修复 + prompt 工程

### 1. 测试 flakiness 根因

`test_parse_named_pois_only` 在两次全量运行中交替 PASS/FAIL。根因不是 JSON 格式错误，而是 LLM 输出风格不稳定：有时发裸 JSON，有时包裹在 Markdown 代码块或说明文字中。

**旧的提取逻辑**：三个测试各有一套 JSON 提取方式——`_get_final_content` 返回字符串，`test_parse_named_pois_only` 自己 try/except 再搜一次。提取逻辑分散，一个路径挂了另一个不一定能兜底。

**修复**：统一为 `_extract_parsed_json()`，直接返回 `list`。三层 fallback：

```
Strategy 1: find("["/"]") → json.loads  → 成功返回
Strategy 2: re.search(r'\[.*\]')        → 成功返回
Strategy 3: json.loads(full_content)    → 成功返回
全部失败: raise AssertionError（含原始内容前 300 字符）
```

所有测试共用这一个函数，不再各自处理。修复后 3 次全量运行 0 失败。

### 2. 新字段的"推断强度"约束

S9 要加 `suggested_duration_h`、`best_time`、`cost_estimate`。三个字段的共性风险是 LLM 会为了"填满 JSON"而编造值。

约束层层递进：

| 字段 | 约束强度 | 关键规则 |
|------|----------|---------|
| `suggested_duration_h` | **类型强制** | 必须是 float，禁止字符串。区间转中值（"3-4小时"→3.5），"半天"→4.0，"一整天"→8.0 |
| `best_time` | **推断门控** | 枚举："morning"/"afternoon"/"evening"/"all_day"。仅有明确表达或强语义暗示时才填。"适合拍照"、"夏天避开中午"这类模糊描述 → null |
| `cost_estimate` | **证据门控** | 仅有明确票价数字时输出（"门票60元"→"门票60元"）。不做"便宜"→数值、"几十块钱"→数值的换算 |

设计思想：**宁可少给信息，不给错信息**。null 比错误值好一万倍。

## S10：从过度工程化到回归本质

### 第一版设计（被否决）

spec 写的是"归一化→别名匹配→同城模糊匹配"，我把它展开成了一个规则管线：

```
输入 → 归一化名称（去"风景区/景区/公园"后缀）
     → 别名匹配（手工维护别名表）
     → 同城模糊匹配（geocode + Haversine + edit distance 阈值）
     → 冲突字段合并（first-non-null 规则）
     → 输出
```

三个问题逐个暴露：

1. **城市字段缺失**：`SourceEntityOut` 没有 `city`，同城匹配需要 geocode 反查或额外字段。这是阻塞性依赖。
2. **别名表维护成本**：10-20 条手工别名能覆盖常见情况，但每次发现新变体都要改代码。
3. **接口形态不确定**：纯函数？API 端点？Agent 内部调用？spec 没说清。

### 用户纠正

> "LLM不再智能了，因为很多问题其实交给LLM都能解决，为什么到Agent设计就如此复杂，结构化输入输出真就这么死板吗？"

### 根因分析

我的错误是把"代码可控"当成了默认正确。规则管线可测试、可调试、无幻觉——这些是代码的优势，但代价是：

- 每个边界条件都要显式处理（后缀表能有多大？edit distance 阈值多少合适？）
- 规则之间相互耦合（城市匹配依赖别名匹配的结果）
- 新增一种名变体就要改代码

而"判断两个 POI 是否为同一地点"这个任务本身是**语义判断**——恰好是 LLM 最擅长的事。在 Agent 系统中引入规则管线解决语义问题，是用错了工具。

### 最终方案

`merge_candidates(sources: list[tuple[str, list[dict]]]) -> list[dict]`：

- 单源 → 短路返回（mention_count=1），不调 LLM
- 多源 → 一次 LLM 调用，prompt 描述合并规则，LLM 自己做语义去重

82 行代码。不需要别名表、不需要 edit distance、不需要城市字段。prompt 里三行规则覆盖了原本要三层管线做的事。

## 方法论沉淀

### LLM 的优势边界

| LLM 擅长 | 代码擅长 |
|-----------|----------|
| 语义相似度判断（"西湖风景区" ≈ "杭州西湖"）| 确定性计算（Haversine、API 调用、DB 查询）|
| 错别字容忍（"雷锋塔" → 知道是"雷峰塔"）| 精确匹配（"雷锋塔" ≠ "雷峰塔"）|
| 上下文消歧（南京鼓楼 vs 北京鼓楼）| 状态管理（事务、并发、缓存）|
| 信息密度不均的归一化 | 结构化格式转换 |

**设计决策树**：

```
这个任务需要判断语义吗？
  ├── 是 → LLM 做（prompt 描述规则 + 约束，不要写代码规则）
  └── 否 → 代码做（Tool 内部闭环，一个函数搞定）
```

### Agent 设计三原则

**原则一：LLM 做判断，代码做执行**

语义任务（解析、去重、路由意图识别）给 LLM。确定性任务（API 调用、数学计算、DB 读写）给代码。不要用规则管线做语义判断，也不要用 LLM 做算术。

**原则二：Tool 内部闭环**

多步骤流程封装在单个 Tool 内（如 `optimize_itinerary` 内含 geocode→matrix→reorder），Agent 只看到原子操作。减少 Agent 的编排负担，同时提供统一降级路径。

**原则三：先单点验证，再抽象复用**

S10 的 merge 是纯函数 + API 端点，没建 Agent，没加中间层。功能验证后再决定是否需要提升抽象层级。过早抽象是 Agent 项目的头号杀手——抽象错了比没有抽象更糟糕。

### 需求明确度自检

V2 五个里程碑，需求明确度递减：

- **A（S11）**：高——用户每一步都看得见
- **B（S9/S10/S13）**：中等——每个子需求明确，但拼起来的具体交互待定
- **C（S12）**：模糊——fact_checker 加搜索后的用户触发时机和体验流程未定义
- **D（S8）**：高——"改 Day2 不影响 Day1/3"用户马上能感知
- **E（S14）**：远期

进入需求模糊的里程碑前，先做场景澄清。否则会在错误方向上过度投资。
